# 评测口径与证据

## 固定数据

32 案例：16 开发、16 保留验证，见 eval/cases.json。每例有输入、固定目录、预期断言、允许结果、禁止行为与人工维度。快照及用例文件哈希保存在 reports/evaluation.json。部分为自然语言对话，部分为确定性接口场景，逐例标注，不能统称为 32 次真实 Agent 测试。

离线比较：v1 30/32，v2 32/32。开发集分别为 15/16、16/16；保留集分别为 15/16、16/16。改善 D07、H14，无已观测退步。只说明这些确定性断言的结果，不说明真实用户收益。

## 一个可复现的策略问题

D07 输入上下文：200 元预算；可选支架 79 元在前、必要键盘 159 元在后。v1 按检索顺序保留预算内条目，结果保留支架而失去必要键盘，虽未超预算却没有满足优先级。

v2 保留原始规则作为 baseline，修复时先排序必要性再保留，结果保留键盘并暂缓支架。H14 换成可选台灯在前的同类边界进行回归。原始前后条目在报告 iteration.evidence 中，不以唯一推荐型号作为所有题目的标准答案。

注意：这不是实际大模型策略效果对比。Prompt v1/v2 和真实模型评测命令已准备，因缺少 API 配置未运行。固定夹具中的单次模型差异将来仍需要重复小样本核实，不能据一次结果宣称稳定提升。

## 其他修复与失败记录

- UI-ENC-01：Windows 默认 GBK 读取 UTF-8 策略配置，初次浏览器发送后返回字段错误。改为显式 UTF-8；直接运行、系统测试与浏览器单品流程复测成功。
- UI-FOLLOWUP-02：代码检查发现尚无方案时，澄清回复含“预算”会被当成已有方案修改。增加“此前已有方案”条件，并新增 BrowserRegressionTests.test_clarification_followup_with_budget_creates_plan。两轮真实 UI 操作现已形成键盘和台灯共 258 元的测试方案。
- FAULT-SEARCH：实验室注入检索超时，运行页记录检索阶段错误，原 229 元键盘方案保留。无搜索成功声明。
- EXT-MODEL / EXT-CART：配置缺失，外部验证未执行，不计为接口成功或失败率分母。

失败类别使用需求理解、检索、资料缺失、推荐约束、计算、状态更新、结算、依赖故障。每次失败保留输入和必要上下文、错误、工具序列；修复关联以用例 ID/测试名和本文记录定位。

## 指标定义

1. 方案有效率：硬约束满足、资料正确、费用披露完整；“没有可行方案”的正确处理单独标注。当前自动断言只覆盖其中确定性部分，真实事实/主观质量不能仅靠代码评分。
2. 结算交接成功率：已确认且适配器支持的方案，返回有效托管结算入口。外部店铺本轮分母 0，故不可计算。本地演练单独验证。
3. 依赖故障正确处理：保留方案、提示正确、无重复操作或假成功。见对应系统测试与 /lab 记录。
4. 真实成交：无可信订单回传，不可测。用户标记与本地演练不纳入。

报告记录通过/失败分母与案例、工具/模型次数、可得 token、延迟和费用可用性。中位延迟只针对有计时的案例，且本地机器/热缓存条件不同，不宣称性能提升。估算费率缺失即 unknown，不以 0 冒充。

## 人工评分（尚未进行）

## 重跑

`python evaluate.py --mode offline` 运行系统与离线案例并保存报告。

配置后先 `python evaluate.py --mode live --version v2 --limit 1`；再明确预算运行 `--version both --split holdout --limit 3`。这仅是三个真实模型案例，绝不可写成完整保留集。若根据保留集调参，应重新标记为开发数据或另建新保留集。

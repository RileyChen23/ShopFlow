## Benchmark

40 个案例包含 48 轮对话。判断基于任务状态和工具 Trace，不匹配固定自然语言答案，也没有使用 LLM Judge。

| 场景 | 案例数 | V1 任务成功 |
|---|---:|---:|
| 正常组合采购 | 6 | 4/6 |
| 预算及硬约束 | 8 | 4/8 |
| 动态修改 | 8 | 1/8 |
| 信息不足与必要追问 | 5 | 4/5 |
| 约束冲突 | 4 | 4/4 |
| 搜索与信息异常 | 5 | 3/5 |
| 购买确认边界 | 4 | 1/4 |
| **合计** | **40** | **21/40** |

演练范围使用固定测试商品，以便确定性核验金额和型号；`real` 范围使用固定的外部搜索响应，以便 V2 完全复用相同搜索输入。模型调用是真实 DeepSeek API 调用，本次没有调用 Tavily，因此这些数字不能解释为实时全网检索质量。

任务成功采用严格合取口径：主要状态断言、工具规则、动态修改、澄清和边界均需通过。B02 最终形成未确认方案且没有购买，但一次工具参数错误仍使严格任务成功判为失败；因此 52.5% 不等同于“用户最终没有得到任何可用结果”的比例。

## Badcase 归因

19 个失败案例按主要根因归入下表。类别互斥以便统计；同一案例的诱因仍保留在原始 Trace。

| 主要层级 | 数量 | 案例 | 直接证据与判断 |
|---|---:|---|---|
| 终止策略 / 搜索效率 | 6 | N03、H03、H05、H06、E02、B01 | 都到达单轮 5 次上限；已完成多次搜索或证据读取，却没有调用 `set_plan`。其中 5 例最终为空方案。 |
| 工具顺序与失败恢复 | 4 | N01、D01、D03、B03 | `set_plan` 在证据未读时被服务端拒绝，之后才 `read_evidence`，但没有剩余工具请求重新提交。 |
| 动态状态管理 | 5 | D02、D04、D05、D06、D08 | 首轮空方案使后续“保留/替换”失去基线，或第二轮删除旧条目后没有提交新条目；D02 还对不存在的条目调用 `update_item`。 |
| 供应商瞬时故障 | 1 | H02 | 搜索和证据读取后，第五次模型请求出现连接/响应异常；本轮事务没有提交。 |
| 成功状态的异常回滚 | 1 | C04 | `set_plan` 已成功，但后续文字回复请求失败；`agent.run` 抛错后，已验证方案没有返回给调用方。 |
| 外部数据 / 固定响应语义 | 1 | E03 | 模型已搜索并读取外部证据，但固定摘要自称“只用于验证”，模型据此拒绝形成待核价候选。该响应与案例期望存在语义张力。 |
| Tool schema 参数 | 1 | B02 | 首次 `update_constraints` 多传 `scope`，schema 明确拒绝；模型随后恢复并形成未确认方案，但严格 Tool correctness 失败。 |

最普遍的表面现象是调用额度耗尽：19 个失败案例中 18 个至少有一轮用满 5 次，11 个失败案例在某轮搜索不少于 3 次。Trace 进一步显示它不是单一根因：有的在重复搜索，有的在错误工具顺序后没有恢复，有的在状态更新后缺少最终提交。

### 代表案例

**N01：明确单品仍未提交**

工具轨迹为 `update_constraints → search_products → search_products → set_plan(failed: 资料缺失) → read_evidence`。模型找到了 `test-kbd1-o`，但先提交后读证据；第五次请求只剩文字回复额度，最终任务条目为 0。根因位于工具顺序和终止恢复，不是商品检索无结果。

**D06：替换过程中提交了空方案**

首轮成功写入 `test-kbd1-o`。第二轮记录蓝牙偏好、搜索、删除旧键盘、读取 `test-kbd2-o` 证据，却没有再次 `set_plan`；最终方案为空。预算仍正确，但新商品约束失败。根因位于多步骤状态更新缺少事务级后置条件。

**C04：方案成功后被回复故障回滚**

Trace 中 `set_plan` 已成功，随后供应商请求失败。Agent 使用任务副本执行，异常路径没有返回已验证的暂存方案，因此外部观察状态为空。原需求要求“模型超时保留方案”，这一点在 V1 未满足。

## 人工抽查

人工检查了 N01、N04、H01、D02、D05、D07、C01、E04、B02 共 9 例，对照最终状态、工具事件和冻结断言，9/9 与自动判分一致。

D05 有构念效度限制：首轮只说“先选一盏台灯”，没有明确要求低价款，但动态断言要求之后移除低价报价。V1 不改案例或成绩；V2 必须原样复测，同时在解释动态指标时继续披露该限制。

## V2 优化优先级

1. **状态机与终止条件**：把“搜索、读取依据、提交方案、最后回复”的阶段和剩余调用数显式化；在最后一次工具机会前阻止继续扩搜。不要单纯提高请求上限。
2. **Tool contract**：`set_plan` 的资料缺失结果返回机器可读的缺失报价 ID 和允许的下一步；读完缺失证据后，对同一份已校验参数提供一次有界重试路径。
3. **动态修改事务**：替换操作在新条目成功写入前不移除旧条目，或在回合结束前验证“用户新要求已落入方案”；空方案不能仅因预算断言通过而被视为有效更新。
4. **成功状态保留**：`set_plan` 成功后即使最终自然语言回复超时，也返回已验证暂存方案并标记“回复失败/待解释”，避免丢失已完成工作。
5. **工具集合与上下文**：当前任务已提供时减少 `get_task` 的可见性；只改数量或删除时优先暴露 `update_item`，降低重新搜索机会。仍由模型决策，不为案例写关键词分支。
6. **Prompt 最后调整**：现有 Prompt 已写明“先读依据”“少搜索”“留最后回复额度”，Trace 证明文字提醒不足。先修前四层，再用同一 40 例判断是否还需改 Prompt。

V2 不应针对案例 ID、固定句式或报价 ID 写分支，也不应修改本 benchmark、搜索响应或判分规则。若修正 E03/D05 的 benchmark 设计，应另建 V2.1 评测集，不能替换这组前后对比数据。

## 可复现命令

先确认代码基线：

```powershell
git checkout eval-baseline-v1
```

评测器和 benchmark 收录在本报告对应的后续评测提交中。配置本机 `.env` 和独立调用预算后，小跑与续跑命令为：

```powershell
python evaluate_agent.py --ids N01,D01,E03 --max-calls 20 --output reports/agent-eval-v1-baseline-final.json
python evaluate_agent.py --resume --max-calls 220 --output reports/agent-eval-v1-baseline-final.json
python evaluate_agent.py --resume --finalize-only --output reports/agent-eval-v1-baseline-final.json --manual-review reports/agent-eval-v1-manual-review.json
```

V2 对比必须复制同一 `eval/agent-benchmark.json` 和固定搜索响应，并核对报告中的 commit、benchmark SHA、Prompt SHA、模型、每轮 5 次上限和评分版本。

## 可安全用于简历的数字

> 为 ShopFlow 搭建覆盖组合采购、88 项硬约束、8 个动态修改任务、工具调用与购买边界的 40 项端到端 Agent 评测集；基于 205 次真实 DeepSeek 请求和 242 次工具调用保存逐案例 Trace，测得 V1 任务成功率 52.5%、硬约束条目满足率 79.5%、动态修改成功率 12.5%、边界违规率 0%，并将 19 个失败案例归因到终止策略、工具契约、状态管理和数据质量等链路。

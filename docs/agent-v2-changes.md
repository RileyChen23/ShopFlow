# ShopFlow Agent V2 机制修改

V2 针对 [V1 正式评测](agent-evaluation-v1.md) 的 Trace 做链路修复。没有修改 `eval/agent-benchmark.json`、固定搜索响应或评分函数，也没有根据 case ID 分支。

## 状态机与终止策略

- 服务端记录本轮目标品类、已返回品类、已读报价、待提交方案和方案更新状态。
- 一个目标品类得到非空结果后，下一次工具 schema 只保留尚未搜索的目标品类；全部目标品类已有结果后隐藏 `search_products`，进入证据与提交阶段。
- 最后一次模型请求在存在搜索结果、已读证据或待提交方案时仍可调用收口工具；只有无需继续工具时才保留为纯文字回复。
- 方案已经成功更新后，后续请求不再暴露工具，避免成功后重复检查或再次搜索。

对应 V1：N03、H03、H05、H06、E02、B01 的重复搜索或证据读取后未提交。

## 证据前置条件与恢复

- `set_plan` 在证据不足时不修改任务，返回 `awaiting_evidence`、`missing_offer_ids`、`required_next_tool` 和 `pending_plan_staged`。
- Agent 读取全部缺失依据后，控制器通过不对模型暴露的 `commit_pending_plan` 进行一次有界提交；该事件完整记录在 Trace。
- 搜索结果明确返回 `offer_ids` 和有序下一步：先读取准备采用的报价，再在同一批工具调用中提交方案。

对应 V1：N01、D01、D03、B03 的“先提交、后读依据、无额度重试”。证据校验没有放松，未读报价仍不能进入方案。

## 动态修改事务

- 根据已有方案和本轮修改类型收窄工具集合：数量调整只暴露状态补丁工具；预算降低或删除不开放搜索；替换场景不开放先删除旧条目的路径。
- 新增 `replace_item` 原子替换：验证新报价依据、预算、币种和约束后一次替换；任一校验失败都保留旧方案。
- `update_item` 继续负责数量、必要性和单项删除，未提及条目保持不变。

对应 V1：D02、D04、D05、D06、D08 的首轮状态缺失、整份方案重建和先删后加问题。

## 成功状态与自然语言回复解耦

- `set_plan`、`update_item` 或 `replace_item` 成功后，若最终模型回复超时、连接失败、格式错误或达到调用上限，返回基于已验证状态的确定性简短摘要。
- Trace 标记 `fallback.type=validated_state_summary`、失败类别和 `status=partial`；任务状态仍可保存，且购买保持未确认。

对应 V1：C04 已成功 `set_plan`，但最终回复失败导致整轮回滚。

## Tool contract

- `update_constraints` 与 `update_item` 描述明确禁止传入 `scope` 等只读字段。
- schema 错误返回允许字段、错误码、状态未变化和恢复动作。
- `task_view.agent_workflow` 暴露阶段顺序、当前方案报价 ID、状态补丁策略和购买边界。

对应 V1：B02 多传 `scope`；同时降低其他工具参数错误的恢复成本。

## E03 夹具判断

E03 的固定外部摘要含“只用于验证”的非业务措辞，和“形成价格未知候选”的预期存在语义冲突。这属于夹具语义问题。为保持 V1/V2 公平，本轮不修改该固定响应；V2 仍按原输入运行，并在结果中单独披露。若以后修正，应建立新的 benchmark 版本，不能替换本次前后对比。

## 确定性验证

新增回归覆盖：阶段工具收窄、搜索品类枚举、证据暂存与一次恢复、原子替换成功与回滚、动态修改路由、只读字段错误结构、最终回复失败后的状态保留。代码修改后的本地结果为 98/98 Python 测试和 19/19 页面数据测试通过。

# 产品说明与实现边界

## 用户与待验证假设

目标用户为宿舍、居家学习与办公的人群。假设他们在“找到候选、比较资料、决定先买什么、准备购买”上存在重复劳动。当前没有访谈或真实试用证据；不能把此假设写成已验证需求。

价值是完成采购任务，不是无限推荐商品流。用户条件明确时直接检索；模糊的桌面改善目标先确定优先问题；可以建议暂缓。单品与组合从需求推导，不强迫选模式。

## MVP 优先级与取舍

P0：可解释方案、确定性预算、来源快照、修改一致性、明确确认、真实区分购买状态。P1：偏好、历史、trace、评测。数据与外部结算是当前最大的待验证依赖。

采用一份 SQLite 任务状态，网页和对话使用同样的领域函数，避免双状态漂移。单 Agent 只做理解、工具选择和解释；金额、数量、身份、预算与确认由代码处理。小资料集用结构化检索，不引入向量库。没有多 Agent、支付托管或全网最低价承诺。

真实模式使用 4 个官方资料型号；演练使用 10 个独立虚构样品。由于没有核实到足够可靠的中国市场报价，没有凑足 30—50 个型号，也没有杜撰人民币价格。真实资料的可购买性因此明显不足，这是产品验收缺口。

## 数据语义

- Product / Variant / Offer：catalog.json 分开保存商品、具体规格、报价身份。事实有字段和摘录来源；图源独立记录。
- ShoppingTask：目标、约束、对象、已有品、排除项、方案快照、修订、确认、消息与状态。
- Preference：用户主动保存的文本与已有品，作用范围 self、来源、更新时间；不是聊天自动画像。
- Run / ToolEvent：每次运行的模式、模型、Prompt、策略、目录版本、输入摘要、工具参数、结果、错误与延迟。代码 commit 默认 unknown。
- Evaluation：固定案例、分组、断言、每轮实际结果和人工待评分项。

## 状态与确认

消息先保存；模型只修改暂存副本。结束时按 revision 做数据库条件更新，旧响应不能覆盖期间的新修改。确认包含本修订的指纹；修改会失效。创建购物车前再核对当前目录与快照，价格变化拒绝交接。

同任务同版本在数据库中只有一条购物车记录。失败或不确定结果不盲目重发。确认后按商家分别交接，外部链接只能记为跳转；本地演练与用户标记也不能写成真实已支付。没有订单 webhook。

## 当前局限

- 真实模型理解和实际 Shopify Cart 接口尚未验证；适配器合同测试不是外部集成测试。
- 离线解析支持有限表达，不支持任意否定、型号简称、复杂多轮或完整自然语言替换；遇到不支持的修改应使用页面控件。它只是可见的离线测试器。
- 兼容性给出资料与待核实事项，没有主机型号数据库，因此不会保证 USB-C 视频输出/供电或完整配套可用。
- 真实优惠、税费、配送与实时库存没有接入；未知费用不会进入最终总价。
- 本地匿名会话不是跨设备账户体系。生产限流、运维、数据保留政策仍需针对实际部署补充。

AI PM 能力对应：需求范围与不做清单、必要澄清与确认设计、Agent/规则边界、证据建模、成功指标与 bad case、版本回归及诚实披露依赖限制。
